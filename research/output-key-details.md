# Key metadata and the cost of detailed output

Research date: 2026-11-20. Product baseline: RegQry v0.1.3, commit `337b568bd77f48bb778a88ab62adde7ee1b91721`. This report supplies facts for the second output-design round. It does not select fields, defaults, an output schema, when additional reads occur, or how their failures affect exit status.

The existing dependencies can obtain the requested key summary. The important cost boundary is access to the owning key; complete value presentation mainly adds data flow and output work. The evidence below separates additional opens/reads from reuse of bytes, time, and environment. No timing benchmark was run.

## Evidence categories and scope

- **Documented:** Microsoft Win32 API documentation; protocol documentation is identified separately where it is more explicit than the Win32 page.
- **Released-source fact:** the actual `winreg 0.56.0` and `windows-sys 0.61.2` packages selected by the baseline lockfile, not their current development branches.
- **Local fact:** baseline source and its existing contract. Relative source links in this report refer to that same baseline.
- **Inference / unverified:** consequences of those facts, with no claim of workstation or supported-platform runtime validation.

Only documentation, source inspection, archive hashes, and a compilation-only probe were used. No live registry query, registry fixture, registry modification, product change, release change, or credential change was performed.

## What the native operations return

`RegQueryInfoKeyW` accepts an already-open key with `KEY_QUERY_VALUE`. Its optional scalar outputs include subkey count, value count, and a `FILETIME` for the last modification of the key or one of its value entries. Optional outputs can be omitted; class text and its length may both be null. The function reports one success/error status, rather than a status for each output. Only a successful result establishes the returned information. [Microsoft API contract](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regqueryinfokeyw).

| Requested information | Meaning and boundary |
| --- | --- |
| Direct subkey count | Counts the next level under this key, not recursive descendants or matched results. This follows from the registry tree structure and Microsoft's example using this count to enumerate that key's immediate children. [Registry structure](https://learn.microsoft.com/en-us/windows/win32/sysinfo/structure-of-the-registry), [enumeration example](https://learn.microsoft.com/en-us/windows/win32/sysinfo/enumerating-registry-subkeys). |
| Actual value count | Counts value entries associated with this key. It is not a sum of bytes, a count of matching values, or a count of readable descendants. An existing unnamed value is one of these entries; an absent default value is not an extra entry. The latter is a deduction from the value-count definition and the documented unnamed-value rules. [Information API](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regqueryinfokeyw), [unnamed values](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regqueryvalueexw). |
| Last-write time | A property of the owning key, not an independent timestamp for each value and not a documented recursive maximum over its descendants. The documented wording does not establish an exhaustive list of which structural/security operations update it. Do not add such a list to the product contract from this research. [Key basic information](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ns-wdm-_key_basic_information). |

`FILETIME` stores unsigned high/low halves of a count in 100-nanosecond units from 1601-01-01 UTC. Units do not prove that every registry update has 100-nanosecond measurement accuracy or that timestamps provide a change sequence number; neither guarantee was found in the cited registry contracts. [FILETIME definition](https://learn.microsoft.com/en-us/windows/win32/api/minwinbase/ns-minwinbase-filetime).

For default-value semantics, a null or empty value name queries the unnamed value; it need not exist and can have any type. `RegQueryValueExW` returns `ERROR_FILE_NOT_FOUND` for an absent value. Therefore a successful count of zero implies no actual values at that observation; a positive count alone does not establish whether the default exists. An actual `REG_NONE`, empty string, or zero-byte value still contributes one entry. These are semantic deductions, not executed fixtures. [Value-query contract](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regqueryvalueexw).

## Existing read lifecycle and additional work

The current `Source` offers root/child opens, indexed child/value enumeration, and full value reads; it has no metadata operation. `Child` already contains `name` and `modified`. The Windows adapter obtains that time in the same successful `RegEnumKeyExW` call that obtains the child's name. Microsoft requires `KEY_ENUMERATE_SUB_KEYS` on the parent for that operation. [Local interface and adapter](../src/registry.rs#L212-L232), [timed enumeration](../src/registry.rs#L298-L333), [native enumeration contract](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regenumkeyexw).

Root and traversal opens request only enumeration permission plus the selected view flag. Value processing separately opens the child with query permission. A key result can currently be emitted before that child is opened for further traversal. `Target` carries identity, not metadata; `Sink::key` receives only the target, while `Sink::value` receives an optional borrowed `RawValue`. Neither callback receives the environment. Thus obtaining data and making it available to output are separate gaps. [Open permissions](../src/registry.rs#L394-L441), [targets / sink](../src/query.rs#L159-L209), [value-processing scope](../src/query.rs#L274-L353), [traversal / emission order](../src/query.rs#L464-L497).

| Detail | Already available at the relevant call site | Additional work if that detail is selected |
| --- | --- | --- |
| Time used for key filtering | `Child.modified` from parent enumeration, used before emission for both key and value searches. [Key filtering](../src/query.rs#L82-L96). | Passing this observation to output requires no additional registry operation. A later fresh time is a different observation. |
| Counts for a key result | No counts and no query-capable child handle at key emission. | With the current permission split, a separate child open requesting `KEY_QUERY_VALUE`, then one metadata call, can obtain them. Combining permissions into the traversal open is an alternative implementation choice, with different access-failure consequences; this report does not choose it. |
| Owning-key summary for value results | The query-capable key handle is alive throughout `Run::values`. | One metadata call in that scope can serve multiple value results from the key without another open. Querying once per value is not inherently required by these APIs. This is a call-site inference, not a new caching design. |
| Complete saved value data | The emitted `RawValue` already has all bytes, the saved type code, and the lossless value name. [Read path](../src/registry.rs#L361-L391), [raw representation](../src/value.rs#L7-L33). | Complete presentation does not require rereading the value. Serialization/escaping and output volume still cost CPU, allocations, and writes. |
| Expanded text | The saved string and query's captured environment are available to matching. [Expansion matching](../src/query.rs#L124-L151). | Derivation and data flow to output; no registry read solely for expansion. See below. |

These are counts of application operations, not latency or complexity guarantees about Windows internals. One summary call avoids opening every child or reading every value to calculate counts, but the examined documentation promises neither constant running time nor a particular overhead. The existing wrapper requests only scalar metadata, so there is no class-buffer growth loop to inherit. [Released wrapper](https://docs.rs/crate/winreg/0.56.0/source/src/reg_key.rs#422-443).

Moving a later metadata timestamp into the filter would change which observation the filter uses. The existing contract applies the owning key's enumerated time to value results. Whether details reuse that observation or report a later measurement is a decision for the design ticket; it must not happen accidentally through a formatter. [Matching contract](../docs/matching.md), [filter call site](../src/query.rs#L464-L470).

## Registry view and symbolic-link identity

Metadata has no separate view selector: it queries its supplied handle. Subsequent child opens must explicitly preserve the selected WOW64 flag. The flags have no effect on shared keys, so two requested logical views need not mean two different physical stores. On native ARM64, Microsoft's documented `KEY_WOW64_32KEY` selection is the x86 view. The current adapter already propagates view flags and separates emitted identities by view. [Microsoft alternate-view rules](https://learn.microsoft.com/en-us/windows/win32/winprog64/accessing-an-alternate-registry-view), [current opens](../src/registry.rs#L394-L423), [identity comparison](../src/query.rs#L166-L183).

For links, the local contract deliberately resolves an explicit search root normally and opens each recursively encountered child component with `REG_OPTION_OPEN_LINK`. The Win32 open page lists the option tersely. Microsoft MS-RRP is more explicit: opening a link without that option resolves its target; opening with it returns the source handle. That is a protocol specification, not a local-Win32 experiment. Querying metadata on the correctly opened handle follows its object identity; reopening the displayed full path with ordinary options can instead resolve a target. This last consequence is an inference from the documented open behavior and current call sites. [Project contract](../docs/architecture.md), [adapter](../src/registry.rs#L394-L423), [Win32 open](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regopenkeyexw), [MS-RRP symbolic links](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rrp/d5ce9dcc-1f90-4f5a-b076-cc1d2c9b4195).

MS-RRP specifies a link source with a `REG_LINK` entry named `SymbolicLinkValue` and no subkeys. That describes source information rather than target contents. It is not permission to substitute hard-coded zero counts: an actual metadata operation can still fail. Nor should the protocol's broken-target error code be promised as the exact local Win32 failure for every link race. [Protocol link model](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rrp/d5ce9dcc-1f90-4f5a-b076-cc1d2c9b4195).

**Unverified boundary:** `RegEnumKeyExW` documents the enumerated child's last-write time but does not explicitly discuss link-source versus link-target timestamps. Source interpretation is consistent with the project's traversal contract; no local link-time comparison was run here. A metadata query on a source-opened handle has clearer handle provenance, but is later and requires query permission. This distinction should remain visible when choosing time provenance. [Enumeration API](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regenumkeyexw).

`HKCR` also denotes a merged logical view under Windows' documented merge rules. A reported summary should not be described as the sum of two physical stores or a timestamp maximum manufactured by RegQry. The cited merge documentation does not specify an aggregation rule for last-write time; exact physical provenance of such a timestamp remains unverified here. [Merged HKCR rules](https://learn.microsoft.com/en-us/windows/win32/sysinfo/merged-view-of-hkey-classes-root).

## Live changes, permissions, and independently unavailable details

Enumeration and query rights are distinct; `KEY_READ` bundles additional rights. Open requests are checked against the key's security descriptor. Consequently, being able to enumerate a parent and obtain a child's name/time does not establish the ability to open that child with query permission. A metadata feature can introduce a new denial boundary in a previously useful key search. This is a consequence of the documented rights, not an observed ACL fixture. No elevation or write permission is necessary merely to request the three metadata fields. [Registry rights](https://learn.microsoft.com/en-us/windows/win32/sysinfo/registry-key-security-and-access-rights).

Windows documents unordered key/value enumeration and warns against changing the enumerated key during the enumeration. It does not promise a consistent snapshot spanning parent enumeration, value reads, metadata, and output. Reusing a handle avoids another path resolution, but does not make separate calls atomic. Therefore a count can differ from the number of subsequently enumerated or emitted records; an earlier filter time can differ from a later summary time. These are concurrency inferences, consistent with the existing live-read contract, rather than detected corruption. [Key enumeration](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regenumkeyexw), [value enumeration](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regenumvaluew), [project contract](../docs/architecture.md).

| Boundary | What can be known, and what cannot be invented |
| --- | --- |
| Metadata open / call fails | Counts are unavailable, not zero. A successful earlier enumeration time may remain available with its earlier provenance. The native metadata operation has one status; it does not provide a supported way to salvage selected zero-initialized fields from a failed call. [Native result contract](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regqueryinfokeyw), [wrapper error path](https://docs.rs/crate/winreg/0.56.0/source/src/reg_key.rs#422-443). |
| ACL changes between operations | A later open is checked against permissions then. Do not claim that every existing handle is automatically revoked, or that every later operation must succeed: individual APIs specify their own handle/access requirements. No dynamic-ACL behavior was tested. [Open contract](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regopenkeyexw). |
| Key disappears / is replaced after enumeration | The later open can fail; `RegOpenKeyExW` does not recreate a missing key. A new open of the same path can also observe a replacement, so path identity is not a cross-call snapshot guarantee. The replacement point is an inference. [Open contract](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regopenkeyexw). |
| Key is deleted while a handle remains | Windows retains a deleted key until its last handle closes and defines error 1018 (`ERROR_KEY_DELETED`) for operations on a key marked for deletion. Neither fact guarantees that every deletion race returns exactly that code from every API. Preserve the actual failure rather than reinterpret it as an empty key. [Deletion lifecycle](https://learn.microsoft.com/en-us/windows/win32/sysinfo/writing-and-deleting-registry-data), [system error definition](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--1000-1299-). |
| Value disappears after its name was enumerated | Its later data query can return `ERROR_FILE_NOT_FOUND`; this does not retroactively make the earlier successful enumeration a snapshot of the later key. [Value-query contract](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regqueryvalueexw). |
| Metadata succeeds, display conversion fails | Raw time and counts can remain valid observations while the chosen time representation is unavailable. Conversion failure is distinct from metadata-read failure. [Conversion API](https://learn.microsoft.com/en-us/windows/win32/api/timezoneapi/nf-timezoneapi-filetimetosystemtime). |

The current bounded retry loop handles changing name/data buffers, discards unsuccessful output, and checks cancellation before further allocations. `query_info` has no such buffer loop and supplies no consistency token. Extra retries cannot be claimed to prove a snapshot. The current `Run::error` makes necessary query errors incomplete, but that existing behavior does not decide the policy for new optional detail reads. [Current buffer adaptation](../src/registry.rs#L249-L296), [current query errors / summary](../src/query.rs#L210-L249), [released wrapper](https://docs.rs/crate/winreg/0.56.0/source/src/reg_key.rs#422-443).

## Full saved data and EXPAND_SZ derivation

`RawValue` retains `OsString`, a `u32` type code, and the full saved `Vec<u8>`. Its `OnceLock` shares decoded text/list/integer data between matching and presentation. The raw read already uses the successful saved length rather than preview limits. A missing default is represented separately with no `RawValue`. Full bytes therefore remain available even when typed interpretation fails, and an absent default has no type/bytes to serialize. [Representation / decoder](../src/value.rs#L7-L104), [read implementation](../src/registry.rs#L361-L391), [default confirmation](../src/query.rs#L327-L353).

A key result itself contains no value payload. Including contents of values that were not read for an emitted value result would require additional enumeration/reads and a scope decision. Also, the existing `confirmed_value_missing` classification is used specifically after a default-value read; applying it to a failed key open or metadata call would conflate a missing key with a missing default. [Key/value emission](../src/query.rs#L253-L272), [default-read call site](../src/query.rs#L327-L353), [error classifier](../src/registry.rs#L216-L218).

String data read through `RegQueryValueExW` is not guaranteed to contain proper terminators. The current decoder intentionally keeps raw bytes, removes at most one final NUL for SZ/EXPAND_SZ, and can report malformed UTF-16. Completing output must use those saved bytes and shared interpretation rather than assume a fresh null-terminated string. This preserves an already-established local distinction between raw data and interpreted text. [Microsoft string warning](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regqueryvalueexw), [local decoding contract](../docs/architecture.md), [decoder](../src/value.rs#L51-L104).

The CLI captures `Environment` once with `vars_os` and passes it to execution. Expansion uses the saved EXPAND_SZ text, nearest percent pairs, ordinal case-insensitive name comparison, and one nonrecursive pass. Unknown names, empty `%%`, and unmatched percent signs stay literal; empty replacements substitute empty text. Neither the selected registry view nor a later metadata read changes this captured environment. These are project semantics, not a claim that RegQry calls the Windows expansion API. [Capture / execution](../src/cli/mod.rs#L249-L278), [implementation](../src/value.rs#L106-L145), [matching contract](../docs/matching.md).

The expanded string is currently temporary matching work: it is not stored in `RawValue` and is not passed to `Sink`. Complete expanded text can reuse the same captured environment and shared decoded text; repeating expansion adds CPU and allocation but no registry access. A list of references/resolution results would require additional derivation/data flow because the existing API returns only the string or an error. It would still not inherently need another registry read. These are local data-flow inferences, not a choice to add those fields. [Expansion call site](../src/query.rs#L134-L145), [expansion return type](../src/value.rs#L115-L145), [sink](../src/query.rs#L203-L209).

Raw bytes can succeed while decoding fails. Decoding can succeed while expansion fails because a selected environment replacement has invalid UTF-16 or an ordinal comparison fails. The saved value does not become absent or empty in either case. Conversely, unknown environment names remaining literal are current successful expansion semantics, not an expansion error. No representation or exit policy for these distinct outcomes is selected here. [Raw / interpreted state](../src/value.rs#L7-L104), [environment error paths](../src/value.rs#L115-L145).

## Inputs still requiring decisions or runtime evidence

The design ticket must choose which details are requested, whether time means the filter's enumeration observation or a fresh metadata observation, when summary reads occur, how unavailable/read-failed/interpretation-failed/not-applicable states appear, and whether additional failures affect completeness or exit status. The report provides no defaults for these choices.

Runtime evidence is still missing for local link-source versus target enumeration timestamps, target deletion and replacement races, dynamic ACL cases, merged-HKCR time provenance, and measured overhead under large/active keys or slow output consumers. Existing architecture describes live reads and synchronous streaming; this research neither changes that contract nor establishes platform/release acceptance. [Baseline architecture](../docs/architecture.md), [synchronous output](../src/output.rs#L168-L208).
