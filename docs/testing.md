# Testing

Tests cover the actual CLI argument contract, pattern/type/root/time validation, query grouping and completeness, raw value interpretation, environment expansion, and fixed output. CLI subprocess tests exercise help/version and invalid input without registry access. Run `cargo test --locked` or the contribution check script.

Integration tests find the CLI relative to their runtime executable, or use the explicit `REGQRY_TEST_BIN` path. They do not embed the build machine's absolute directory. The portable test runner supplies the bundled CLI explicitly.

Query tests use deterministic in-memory sources and a native temporary application hive. RegLoadAppKey creates a new hive inside a unique temporary directory; setup writes only through that private handle. The native case covers a 6,000-character value name, a 256 KiB value, an unknown type code, exact saved bytes and the query/output path; closing all handles and explicit temporary-directory cleanup are checked. Ordinary tests do not create globally navigable registry fixtures or request elevation. Application hives do not prove CLI ROOT, WOW64 view separation, or per-child ACL behavior.

Additional native cases preserve unpaired UTF-16 surrogates in actual key/value names, round-trip malformed SZ/EXPAND_SZ/MULTI_SZ and integer layouts, and verify that raw/type queries still work while necessary interpretation reports incomplete. Malformed fixtures use the existing windows-sys NtSetValueKey binding (a test-only Wdk_System_Registry feature), with exact raw readback; [RegSetValueExW requires terminated string input](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regsetvalueexw). The [native service uses NtSetValueKey in user mode](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-zwsetvaluekey). Product reads remain on the Win32 adapter.

A coordinated writer thread changes a private-hive value between actual Win32 attempts: growing values exhaust exactly eight retries, while a later shrink/type change returns only the successful saved bytes and type. Deleting a value/key between enumeration and reading preserves Win32 2/1018, continues another readable root, and never invents an unset default. These are controlled changes at API boundaries, not a snapshot or arbitrary mutation stress guarantee.

All three raw operations share one private bounded-buffer loop. Native enumeration probes deliberately start with a small test buffer to exercise real ERROR_MORE_DATA; production starts at 256 units/bytes. Failed name-enumeration output is not used as a capacity hint; ordinary-root value reads use the documented required-byte count. See [RegEnumKeyExW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regenumkeyexw) and [RegQueryValueExW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regqueryvalueexw). Cancellation is checked before growing again. Capacity-overflow probes fail before attempting the allocation; deliberate OS memory exhaustion is not tested.

The query/output path also writes to a real Windows anonymous pipe whose reader is closed, directly and through BufWriter. Both write and flush failures produce status 2 and stop further traversal. This reuses [std::io::pipe](https://doc.rust-lang.org/std/io/fn.pipe.html); the query input is constructed data. It does not replace actual CLI pipeline or console Ctrl+C acceptance. Atomic-flag cancellation tests likewise do not prove delivery of a console event.

Real root/view/ACL/link cases run only in explicitly started, [disposable VM suites](vm-testing.md). The portable bundle includes their ignored harness and a two-phase runner: elevated preparation, then a separate ordinary-user query. Fresh identities, creation dispositions, ownership markers, actual access rights and exact bundle identity are checked. Hosted jobs retain actual run/job lifecycle references and the provider disposal contract; independently managed VMs retain external rollback/destruction records. Never use the user's existing registry as a fixed expected-result dataset.

From a repository checkout, build a development test bundle from the actual Cargo archive, using the pinned native compiler and MSVC tools:

```powershell
./scripts/check.ps1 -Check package
# For this version and the default Cargo target directory:
./scripts/build-test-bundle.ps1 -SourceArchive target/package/regqry-0.1.0.crate -OutputDirectory artifacts/portable-tests
$built = Get-Content artifacts/portable-tests/build.json -Raw -Encoding utf8 | ConvertFrom-Json
./scripts/check-test-bundle.ps1 -BundleArchive $built.bundle.archive -ExpectedArchiveSha256 $built.bundle.sha256 -ExpectedManifestSha256 $built.bundle.manifestSha256
./scripts/test-bundle-gates.ps1 -BundleDirectory $built.bundle.directory -BundleArchive $built.bundle.archive
./scripts/test-vm-gates.ps1 -BundleDirectory $built.bundle.directory
```

Choose a new output directory each time. If `CARGO_TARGET_DIR` is configured, use its `package/` directory instead. Install the pinned cargo-about and rust-docs component first, or pass `-CargoAbout` to an existing matching executable. The builder extracts the archive outside the repository, compiles the actual CLI and all Cargo test harnesses with `-C target-feature=+crt-static`, and obtains executable paths from Cargo's JSON messages. It copies every harness, including empty or ignored inventories; it does not select executables using a loose output-directory glob. Runtime fixtures are currently constructed by those harnesses. Doctests that require rustc stay in build environments.

The bundle includes a manifest of source/lock/commit, toolchain, target, flags, file sizes/hashes, test names and ignored counts. It carries [test-scope license materials](distribution.md), including development dependencies and the actual Rust standard-library notices. The runner verifies those materials and scope before starting any payload. MSVC `dumpbin /IMPORTS` checks direct and delay-load DLLs on every executable, and `/HEADERS` checks the machine code. Dynamic CRT and DLLs outside the reviewed system list fail. Raw tool output and the tool's version/hash are retained. These checks do not prove dynamic LoadLibrary calls, imported API availability or minimum-system compatibility. See the [Rust CRT reference](https://doc.rust-lang.org/reference/linkage.html#static-and-dynamic-c-runtimes) and [Microsoft import inspection](https://learn.microsoft.com/en-us/cpp/build/reference/imports-dumpbin).

Extract the whole ZIP on the matching native architecture and run `./run-tests.ps1` with PowerShell 5.1 or 7. No Rust installation, elevation, or network is required by the test layer. An optional `-ExpectedManifestSha256` binds execution to a separately retained identity. The runner checks the complete payload and test/PE inventories before starting programs, then records actual OS/native/process architecture, user SID/token elevation, shell, executable identity, arguments, exit codes, timings and captured UTF-8 streams. Ignored cases remain explicitly ignored. Reports go to a new directory outside the verified bundle. Hashes establish byte identity, not authentication.

`check-test-bundle.ps1` extracts the ZIP into a new path containing spaces and Unicode, runs from an unrelated working directory, removes Cargo/rustc from PATH, clears inherited test-path overrides and restores its environment afterward. `test-bundle-gates.ps1` uses disposable copies to verify hash corruption, missing/extra files, incomplete harness/PE inventories and the wrong PE architecture fail before payload execution; it can also check a supplied dynamic-CRT executable with `-DynamicExecutable`. Native CI builds and relocates bundles on both architectures and retains the ZIP and records as temporary Actions artifacts.

Build directories and probe copies remain in uniquely named OS temporary directories for inspection; reports identify their locations. Development bundles are not frozen release assets. Final acceptance uses the actual frozen candidate bytes in dedicated native hosted standard-user jobs, with Cargo absent from the query PATH. Hosted/local development runs and a restricted PATH do not establish a clean system; minimum/clean clients remain explicitly unexecuted. Formal evidence and original acceptance ZIPs are archived with the release rather than relying only on expiring Actions artifacts. The [native asset builder](https://github.com/inaku-Gyan/RegQry/blob/main/docs/releasing.md) adds the user ZIP, checks matching CLI/source identities before execution, validates local documentation links, and preserves both archives without replacing them.

The ordinary process-control probe uses a fresh hidden console and kill-on-close job. A constructed producer validates real CTRL_C_EVENT delivery, streaming, closed-pipe handling, and worker timeout cleanup. It has no registry/query-engine input; its CONTROL_PROBE records are not product performance evidence. The ignored [VM process case](vm-testing.md) uses the same apparatus with the actual selected CLI and owned generated registry data, including full long-value matching beyond the preview. Both native hosted jobs have executed it as a standard user for development assets; each frozen candidate still needs its own actual records.

The same isolated console/job now hosts real cmd, Windows PowerShell 5.1 and optional installed PowerShell 7 invocations. Ordinary cases exercise actual help/version and invalid input only; query-shaped commands receive an invalid ROOT so validation finishes before registry access. The [VM shell case](vm-testing.md) uses their successful forms over owned fixtures and requires PowerShell 7. Set `REGQRY_TEST_PWSH` to the installed absolute `pwsh.exe` path for Cargo tests, or pass `-PowerShell7` to the portable/VM runner. CI explicitly selects its own PowerShell 7. Missing automatic discovery is logged `not-run` in ordinary checks; an explicit invalid path fails. No PowerShell version is installed by these tools.

The harness compares direct CLI streams with cmd's raw redirection and PowerShell's string capture, UTF-8 Out-File and version-specific native redirection. It retains every generated script/output's original bytes as SHELL_FILE hex records, plus shell versions, exact reference arguments and exit codes. Expected PowerShell stderr formatting is allowed, while Unicode and diagnostic content must survive. The calling console's code pages are checked before/after; code-page changes occur solely inside the hidden job. These are process-level checks, not visual terminal tests. The [manual terminal record](terminal-validation.md) stays `not-run` until an operator runs the actual console/Terminal matrix.

Record pass, fail, not-run and missing separately. The dedicated [hosted registry jobs](https://github.com/inaku-Gyan/RegQry/blob/main/docs/hosted-acceptance.md) use a fresh local standard user and loaded profile in the same disposable job as elevated fixture preparation. The actual non-elevated ROOT/view/ACL/link/process/shell/scaling results and independent installed-CLI checks remain release gates. GitHub's per-job VM lifecycle and original run/job records provide the accepted isolation evidence; a separate external rollback receipt is not required for these jobs.

Windows 10 22H2, x64 Windows 11, the ARM64 minimum 24H2 build and clean Windows installations remain compatibility targets with unexecuted direct checks, outside the first-release hard gates. Human-visible terminal layout and physical-keyboard input are deferred; automatic output/encoding/exit checks and actual console Ctrl+C events remain required. A restricted PATH is recorded as such. See [validation status](https://github.com/inaku-Gyan/RegQry/blob/main/docs/validation/README.md).

Performance acceptance initially records a baseline rather than a quantitative SLA: first actual result, total duration, peak working set, and Ctrl+C-to-exit time, using fixed generated data and representative live queries. Verify streaming, cancellation 130, long results and no hidden truncation of matching. Deduplication memory may grow with identities; do not assert constant memory or a sorted traversal order.

The [performance tools](performance.md) now generate the full fixed scaling fixture, verify it through a private application hive in ordinary tests, and measure the actual CLI only in the guarded VM scaling case. A constructed-producer probe checks the shared streaming/aggregate consumer and process-memory measurement. It separately verifies that live summaries retain no key/value/data text and that a grouping header is not counted as a result. These apparatus metrics are not RegQry query timings.

The bundle's separate `measure-live.ps1 -ReadOnlyLiveRegistry` makes read-only observations of existing HKCU/HKLM data with a non-elevated token. It uses six fixed queries, twice, and retains only counts, sizes, timing, peak memory and numeric error summaries. It does not create a correctness dataset, save raw registry output or claim a complete query when exit 2 is observed. CI probes its opt-in/identity guards without starting live queries. A separate live report uses status `observed`, not a formal acceptance pass.
